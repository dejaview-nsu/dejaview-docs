# Контракт backend и ML-сервиса

Как backend (C++) вызывает ML-сервис (Python) при поиске и в каком формате ML-сервис и скрипт
индексации хранят векторы в Qdrant. Задача #17626. Машиночитаемая версия разделов 2 и 6 -
[ml-service.openapi.yaml](ml-service.openapi.yaml).

Постановка #17626 писалась, когда ML-сервис только строил вектор. Сейчас поиск целиком выполняет
ML-сервис (wiki [Стек_технологий][stack] разд. 13, [Архитектура_поиска][search] п. 1.5), поэтому:

- вместо эндпоинта векторизации - эндпоинт поиска по модальности (раздел 2);
- формат вектора, метаданные на векторе и параметры индекса - внутренний формат ML-сервиса и
  Qdrant (раздел 3). Backend его не видит, соблюдают его ML-сервис (#17637) и скрипт
  индексации (#17650).

```
клиент ─> nginx ─> backend ──HTTP/JSON──> ML-сервис ──gRPC──> Qdrant
                      │
                      └──> PostgreSQL: карточки по movie_id
```

## 1. Протокол

**HTTP/1.1. Ответы - JSON. Файл запроса передается телом HTTP-запроса как есть, формат - в
`Content-Type`. Текстовый запрос - JSON.**

Альтернативы: gRPC; HTTP с `multipart/form-data`.

Почему:

- При 50 rps (#17093 п. 1.1) выигрыш gRPC в сериализации незаметен: время поиска уходит на
  инференс, до 495 мс на один 10-секундный сегмент видео (#17248).
- gRPC - кодогенерация proto в CMake и в Python, лишний шаг сборки в двух репозиториях.
- HTTP отлаживается curl, а HTTP health check нужен и так (#17098 п. 5.1).
- Файл в запросе один (#17153 п. 4.2.1, #17154 п. 4.2.1, #17155 п. 4.2.1), других полей нет.
  Без multipart backend не собирает его на C++, а ML-сервис не разбирает.

Закрывает: #17093, #17098.

Соединение:

- Внутренняя docker-сеть production (wiki [Схема_развертывания][deploy]), порт ML-сервиса
  наружу не публикуется. TLS и аутентификации между backend и ML-сервисом нет.
- Адрес ML-сервиса - конфигурация backend (wiki [API_service][api]). В примерах - `http://ml:8000`.
- Пути версионируются префиксом `/v1`, кроме `/health`.
- Backend передает в каждом запросе заголовок `X-Request-Id`, ML-сервис пишет его в журнал:
  сбой ищется по одному идентификатору в журналах обоих сервисов (#17098 п. 5.2).

## 2. Поиск по модальности

Backend передает модальность (в пути) и запрос, ML-сервис возвращает список `movie_id` по
убыванию релевантности (#17241, wiki [Архитектура_поиска][search] п. 1.5).

| Модальность | Запрос | `Content-Type` | Ограничения на вход | N |
|---|---|---|---|---|
| текст | `POST /v1/search/text` | `application/json` | 3-250 символов (#17152 п. 3.4) | до 10 |
| изображение | `POST /v1/search/image` | `image/jpeg`, `image/png`, `image/webp` | JPG, JPEG, PNG, WEBP; до 10 МБ (#17153 п. 4.2) | 1 |
| видео | `POST /v1/search/video` | `video/mp4`, `video/quicktime`, `video/webm` | MP4, MOV, WEBM; до 30 с; до 50 МБ (#17154 п. 4.2) | 1 |
| аудио | `POST /v1/search/audio` | `audio/mpeg`, `audio/wav`, `audio/ogg`, `audio/mp4` | MP3, WAV, OGG, M4A; до 10 с; до 20 МБ (#17155 п. 4.2) | 1 |

N - сколько фильмов возвращается: #17152 п. 4.4, #17153 п. 6.1, #17154 п. 6.1, #17155 п. 6.1,
wiki [Архитектура_поиска][search] п. 1.2. МБ здесь и дальше - 1 048 576 байт.

Sprint 1 - изображение и видео, текст и аудио опциональны (#17637 п. 3).

### Запрос

Текст:

```json
{"query": "девушка в красном платье в толпе людей в черном"}
```

Изображение, видео, аудио: тело - байты файла, `Content-Type` - из таблицы. Backend
отправляет тип, который сам определил при проверке формата.

### Ответ 200

```json
{"movie_ids": [603, 604, 605]}
```

- `movie_ids` - целые числа, ключ фильма в PostgreSQL (#17241, #17627), без повторов, по
  убыванию релевантности.
- Не больше N. Меньше N или пустой список - обычный ответ 200, не ошибка: сообщение об
  отсутствии результата показывает backend и интерфейс (#17152 п. 6, #17153 п. 7, #17154 п. 7,
  #17155 п. 7).
- Score не передается (#17392 п. 5, #17152 п. 5.4).
- Порог релевантности - настройка ML-сервиса: если ближайшие фрагменты слишком далеки от
  запроса, фильм не возвращается, и ответ - пустой список («ничего не найдено», #17153 п. 7,
  #17154 п. 7). По умолчанию порог выключен, значение подбирает ML-команда по замерам #17641.
- Карточки по `movie_ids` backend берет из PostgreSQL. ML-сервис в PostgreSQL не ходит.

### Кто что проверяет

| Проверка | Кто | Почему |
|---|---|---|
| Длина текста, недопустимое содержимое (#17152 п. 3.4) | backend | валидация входа - в backend (wiki [Архитектура_поиска][search] п. 1.5) |
| Один файл, формат, размер | backend, размер еще nginx | то же; nginx режет тело больше 50 МБ (wiki [Nginx][nginx]) |
| Файл не поврежден, длительность видео и аудио | ML-сервис | ML-сервис и так декодирует и режет файл через ffmpeg (wiki [Inference_service][ml]), в backend ffmpeg нет |

ML-сервис повторяет проверки backend (тип, размер, длина текста) и на нарушение отвечает 4xx,
а не 500.

### Ошибки ML-сервиса

Тело ошибки:

```json
{"code": "FILE_CORRUPTED", "message": "cannot decode image"}
```

`message` - диагностика для журнала backend. Клиенту ни `message`, ни `code` ML-сервиса не
уходят: backend отвечает своими кодами из `api/openapi.yaml` (#17628, #17094 п. 4.3).

| HTTP | `code` | Когда | Ответ backend клиенту |
|---|---|---|---|
| 413 | `FILE_TOO_LARGE` | тело больше лимита модальности | 413 `FILE_TOO_LARGE` |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | `Content-Type` не из таблицы | 415 `UNSUPPORTED_FORMAT` |
| 422 | `INVALID_QUERY` | текст короче 3 или длиннее 250 символов, JSON не разбирается | 422 `QUERY_TOO_SHORT` или `QUERY_TOO_LONG` |
| 422 | `FILE_CORRUPTED` | файл не декодируется | 422 `FILE_CORRUPTED` (#17153 п. 8.1.5, #17154 п. 8.1.6, #17155 п. 8.1.6) |
| 422 | `DURATION_TOO_LONG` | видео длиннее 30 с, аудио длиннее 10 с | 422 `VIDEO_TOO_LONG` (#17154 п. 8.1.4) или `AUDIO_TOO_LONG` (#17155 п. 8.1.4) |
| 503 | `NOT_READY` | модель модальности загружается или выключена | 503 `SEARCH_UNAVAILABLE` (раздел 5) |
| 503 | `QDRANT_UNAVAILABLE` | Qdrant не отвечает | 503 `SEARCH_UNAVAILABLE` |
| 500 | `INTERNAL_ERROR` | прочие сбои | 503 `SEARCH_UNAVAILABLE` |

413, 415 и `INVALID_QUERY` при исправном backend не возникают: он проверяет то же раньше.

## 3. Векторы и коллекции Qdrant

### Кто обращается в Qdrant

**Только ML-сервис (поиск) и скрипт индексации (запись). Backend к Qdrant не обращается.**

Альтернатива: ML-сервис только строит вектор, backend сам ищет в Qdrant и агрегирует
(весенняя схема).

Почему (wiki [Стек_технологий][stack] разд. 13):

- Результат поиска ML - `movie_id` (#17241).
- Схему коллекций знает одна сторона: ML-сервис и скрипт индексации лежат в одном репозитории
  `dejaview-ml` (#17650).
- У Qdrant нет официального C++-клиента: backend писал бы запросы к REST API вручную и
  дублировал агрегатор на C++.
- Один вызов на поиск вместо двух.

Закрывает: #17392, #17241.

Правила ниже - внутренний формат. Обязательны для ML-сервиса (#17637) и скрипта индексации
(#17650), backend их не видит.

### Коллекции и векторы

| Коллекция | Модель | Размерность | Точка - это | Точек на фильм |
|---|---|---|---|---|
| `text` | `intfloat/multilingual-e5-base` | 768 | описание фильма из TMDB | 1 |
| `image` | `openai/clip-vit-base-patch32` | 512 | кадр, каждые 5 с | ~1200 |
| `video` | `Searchium-ai/clip4clip-webvid150k` | 512 | сегмент 10 с без перекрытия | ~600 |
| `audio` | `laion/clap-htsat-fused` | 512 | чанк 10 с с шагом 5 с | ~1200 |

Размерности - #17392 п. 3, модели - #17248, нарезка - #17395 п. 2.2 и #17393 п. 4, точек на
фильм - #17395 п. 3.1. Коллекции изолированы: запрос ищется только в коллекции своей модальности
(#17392 п. 3).

- Вектор - float32 (#17395 п. 2.2), метрика cosine (#17392 п. 5).
- Запрос и фрагменты фильма проходят через одну модель с одной предобработкой: общий код и одни
  веса в ML-сервисе и скрипте индексации (wiki [Indexing_tool][indexing]). Смена модели или
  ревизии весов - переиндексация коллекции.
- e5 обучена на префиксах: описание фильма индексируется как `passage: <текст>`, запрос
  кодируется как `query: <текст>` (model card `intfloat/multilingual-e5-base`).
- Видеофрагмент запроса бывает до 30 с (#17154 п. 4.2.3), сегмент индекса - 10 с. Как запрос
  сводится к векторам, сравнимым с сегментами, решает #17637. Аудиофрагмент запроса до 10 с
  (#17155 п. 4.2.3) - ровно один чанк.

### Метаданные на векторе

| Поле | Тип | Значение |
|---|---|---|
| `movie_id` | integer | ключ фильма, как в PostgreSQL (#17241) |
| `type` | keyword | `text`, `image`, `video` или `audio`, совпадает с именем коллекции |
| `offset_sec` | integer | начало фрагмента, секунды от начала фильма; в `text` поля нет |

Состав - #17392 п. 4. `offset_sec` целый: шаги нарезки кратны секунде (#17395 п. 2.2).

В каждой коллекции payload index по `movie_id` (integer): фильтр по подмножеству фильмов
(#17392 п. 4) и удаление фильма из каталога (#17393 п. 6).

### Идентификатор точки

ID точки - UUIDv5 в namespace `uuid.NAMESPACE_URL` от строки
`dejaview:<type>:<movie_id>:<offset_sec>`, для текста - `dejaview:text:<movie_id>`.

```python
uuid.uuid5(uuid.NAMESPACE_URL, "dejaview:image:603:125")
```

Повторная индексация фильма перезаписывает те же точки, дублей нет (#17650 п. 6). Если исходный
файл фильма заменили и нарезка изменилась, скрипт сначала удаляет точки фильма фильтром по
`movie_id` во всех четырех коллекциях.

### Создание коллекций

- ML-сервис при старте создает недостающие коллекции с параметрами из таблицы и индексом по
  `movie_id` (#17637 п. 4).
- Коллекция есть, но размерность или метрика другая: ML-сервис не стартует и пишет причину в
  журнал. Коллекцию не пересоздает, иначе потеряется индекс.
- Скрипт индексации пишет в готовые коллекции и их не создает, как скрипты не меняют схему
  PostgreSQL (wiki [Стек_технологий][stack] разд. 11). Коллекции нет - скрипт завершается с
  понятной ошибкой.

### Индекс и поиск

- HNSW с параметрами Qdrant по умолчанию (#17392 п. 5). `m`, `ef_construct`, `ef` подстраиваются
  по коллекциям после замеров #17641 (wiki [Qdrant][qdrant]), контракт при этом не меняется.
- top-K = 20 ближайших точек на запрос (#17392 п. 5), настройка ML-сервиса.
- Агрегация: точки группируются по `movie_id`, score суммируется, фильмы сортируются по сумме,
  берутся первые N (wiki [Архитектура_поиска][search] п. 1.2).
- Запрос в Qdrant - не дольше 200 мс для 95% запросов (#17392 п. 6).

## 4. Таймауты, повторы, лимиты

### Таймауты

Бюджет - SLA цепочки поиска (#17093 п. 2.2-2.5). Отсчет идет с момента, когда backend получил
запрос целиком: загрузка файла пользователем нормируется отдельно (#17093 п. 3.1-3.3). Backend
оставляет себе 1 с на валидацию, выборку карточек и ответ, остальное - срок вызова
ML-сервиса.

| Модальность | SLA, 95% запросов | Срок вызова ML-сервиса | Лимит входа у ML-сервиса |
|---|---|---|---|
| текст | 5 с (#17093 п. 2.2) | 4 с | 250 символов |
| изображение | 10 с (#17093 п. 2.3) | 9 с | 10 МБ |
| видео | 15 с (#17093 п. 2.4) | 14 с | 50 МБ, 30 с |
| аудио | 15 с (#17093 п. 2.5) | 14 с | 20 МБ, 10 с |

- Таймаут из таблицы - общий срок вызова ML-сервиса: установка соединения и повтор входят в
  него. Установка соединения - не дольше 1 с.
- Значения - по умолчанию в конфигурации backend, уточняются по замерам #17641.
- Поиск синхронный: один HTTP-запрос, без очереди и опроса статуса (wiki
  [Стек_технологий][stack] разд. 7). Если замеры #17641 покажут больше 15 с на видео, поиск
  переводится на асинхронный режим отдельным изменением контракта.

### Повторы

- Запрос, который ушел в ML-сервис, backend не повторяет: повтор видео не укладывается в бюджет
  и удваивает нагрузку на единственный GPU (wiki [Inference_service][ml], «Масштабирование»).
- Один немедленный повтор - только если соединение не установилось, запрос не ушел и в сроке
  вызова еще осталось время.
- Дальше повторяет пользователь: файл или текст и кнопка «Начать поиск» остаются на месте
  (раздел 5).

### Параллельные запросы

- Каждый экземпляр backend держит не больше M одновременных запросов к ML-сервису (wiki
  [Стек_технологий][stack] разд. 7). M - настройка backend, стартовое значение выбирает команда
  backend (#17636) и уточняет по замерам #17641 и нагрузочному тесту (#17093 п. 1.4). Сумма M по экземплярам (до 4, #17096 п. 1.3) не больше
  того, что ML-сервис успевает обработать за таймаут.
- Свободного слота нет - backend сразу отвечает 503 `SERVER_BUSY`, не дожидаясь слота. Так
  ответ при перегрузке укладывается в 5 с (#17093 п. 5.1).

### Размер

ML-сервис принимает тело до лимита модальности из таблицы и на большее отвечает 413. Тело больше
50 МБ до backend не доходит: его отсекает nginx (wiki [Nginx][nginx]).

## 5. Недоступность ML-сервиса

| Что случилось | Ответ backend клиенту |
|---|---|
| Нет соединения, таймаут, 5xx, `NOT_READY`, `QDRANT_UNAVAILABLE`, открыт автомат отключения | 503 `SEARCH_UNAVAILABLE` |
| Исчерпан лимит параллельных запросов | 503 `SERVER_BUSY` |
| ML-сервис ответил 4xx | ошибка входа по таблице раздела 2, это не недоступность |

Коды и тексты - из `api/openapi.yaml` (#17628), тело - схема `Error`. Точного текста в
требованиях нет, в OpenAPI поиска зафиксировано:

```json
{"code": "SEARCH_UNAVAILABLE", "message": "Поиск временно недоступен. Попробуйте позже"}
```

```json
{"code": "SERVER_BUSY", "message": "Сервис перегружен. Попробуйте позже"}
```

### Автоматическое отключение вызовов

Прием из риска #17296 (действие 3) применен к ML-сервису:

- 5 сбоев подряд (нет соединения, таймаут, 5xx) - backend 30 с не вызывает ML-сервис и сразу
  отвечает 503 `SEARCH_UNAVAILABLE`. Ответы 4xx сбоями не считаются.
- Через 30 с backend запрашивает `GET /health`. 200 - вызовы возобновляются, иначе еще 30 с.
- 5 и 30 с - стартовые значения в конфигурации backend.

Так при зависшем ML-сервисе пользователь не ждет по 14 с на каждый запрос.

### Что показывает интерфейс

По #17152 п. 8, #17153 п. 9, #17154 п. 9, #17155 п. 9:

- Не показывает результат: ни предыдущий, ни частичный (п. 9.1, для текста п. 8.1).
- Показывает `message` из ответа в области сообщений режима (п. 9.2, для текста п. 8.2; п. 2.1.4).
- Оставляет выбранный файл или текст запроса и доступную кнопку «Начать поиск», чтобы повторить
  (#17097 п. 1.12).
- Пока ответа нет дольше 2 с, показывает состояние обработки (#17097 п. 1.6).

Backend пишет в журнал `code` и `message` ML-сервиса и `X-Request-Id` (#17098 п. 5.2).
Клиенту внутренние детали не уходят (#17094 п. 4.3, #17097 п. 1.5).

## 6. Health check

`GET /health` - 200, если сервис готов к поиску, иначе 503. Тело в обоих случаях:

```json
{
  "status": "ok",
  "models": {"text": "disabled", "image": "ready", "video": "ready", "audio": "disabled"},
  "qdrant": "ok"
}
```

| Поле | Значения |
|---|---|
| `status` | `ok` - все включенные модели `ready` и Qdrant `ok`; иначе `unavailable` |
| `models.<модальность>` | `loading`, `ready`, `failed`; `disabled` - модальность выключена конфигурацией (в Sprint 1 текст и аудио, #17637 п. 3) |
| `qdrant` | `ok` - Qdrant отвечает и четыре коллекции есть; иначе `unavailable` |

- Закрывает #17098 п. 5.1 (статус сервиса и зависимостей) и #17637 п. 7 (готовность моделей).
- Без инференса: health check не грузит GPU.
- Кто вызывает: healthcheck контейнера в docker-compose; backend после автомата отключения
  (раздел 5) и в своем health check как зависимость (#17098 п. 5.1); мониторинг.

```http
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json

{"code": "DURATION_TOO_LONG", "message": "video is 41.2 s, limit 30 s"}
```

Модель видео еще загружается. ML-сервис отвечает backend:

```http
HTTP/1.1 503 Service Unavailable
Content-Type: application/json

{"code": "NOT_READY", "message": "model video is loading"}
```

Backend отвечает клиенту:

```http
HTTP/1.1 503 Service Unavailable
Content-Type: application/json

{"code": "SEARCH_UNAVAILABLE", "message": "Поиск временно недоступен. Попробуйте позже"}
```

Ничего не найдено (коллекция пуста):

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"movie_ids": []}
```
