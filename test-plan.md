# Тест-план этапа реализации DejaView

## 1. Цель

Этот документ определяет, что, где и когда проверяется на этапе реализации DejaView, какие проверки обязательны перед слиянием изменений и после релиза, как фиксируются результаты и дефекты, а также как меняется набор проверок от спринта к спринту.

Тестирование строится по принципу постепенного расширения:

- каждое изменение проходит автоматические проверки в CI;
- функциональность спринта проверяется через API и, после появления соответствующего интерфейса, через UI;
- качество поиска контролируется на фиксированных выборках с известным ожидаемым `movie_id`;
- в Sprint 3 выполняется нагрузочная проверка поисковой цепочки;
- в Sprint 4 проверяются сквозные пользовательские сценарии;
- в Sprint 5 выполняются проверки безопасности и нагрузочный тест системы целиком;
- в Sprint 6 выполняются полное приёмочное и регрессионное тестирование.

План привязан к текущему плану этапа реализации. Если сроки отдельных задач сдвигаются, проверка переносится вместе с готовностью соответствующей функциональности, но её объём и критерии не должны исчезать без отдельного согласования.

## 2. Объект тестирования

В область тестирования входят:

- frontend;
- backend;
- ML-сервис;
- PostgreSQL и миграции схемы;
- Qdrant и поисковая цепочка;
- MinIO в сценариях, где он используется;
- API-контракты;
- контейнеризация и взаимодействие сервисов;
- пользовательские сценарии;
- нефункциональные требования: производительность, безопасность, устойчивость к перегрузке и корректность отката.

## 3. Уровни проверок

### 3.1. Проверки в CI

На каждый Pull Request должны запускаться:

- сборка;
- unit/integration-тесты репозитория;
- проверка стиля;
- валидация OpenAPI и контрактов;
- для backend — проверка миграций на PostgreSQL 16:
  `dbmate up -> rollback всех миграций по одной -> dbmate up`.

Pull Request с обязательной упавшей проверкой не вливается в `main`.

### 3.2. Проверки после релиза

После релиза проверка выполняется на рабочем сервере:

1. smoke-проверка доступности;
2. проверка новой функциональности спринта через API;
3. после готовности UI — проверка основных пользовательских сценариев через интерфейс;
4. фиксация багов в Redmine.

Если основной сценарий релиза не работает, нарушена целостность данных или безопасность — релиз откатывается.

## 4. Проверки по спринтам

### Sprint 1 — поиск по изображению и видео, регистрация и вход

Основная QA-задача — контрольная выборка поиска по изображению и видео.

Для проверки поиска:

- взять 10 фильмов из проиндексированного каталога;
- фильмы должны быть различны по жанрам и визуальному стилю;
- для каждого фильма подготовить 3 изображения и 2 видеофрагмента до 30 секунд;
- для каждого теста заранее зафиксировать ожидаемый `movie_id`;

Проверить:

**Валидные запросы**

- для каждого изображения и видеофрагмента система возвращает ожидаемый `movie_id`;
- HTTP-статус и структура ответа соответствуют `api/openapi.yaml`;
- время ответа соответствует #17093:
  - не менее 95% запросов по изображению выполняются не более чем за 10 секунд;
  - не менее 95% запросов по видео выполняются не более чем за 15 секунд.

**Некорректные запросы**

Проверить:

- запрос без файла;
- запрос с двумя файлами;
- неподдерживаемый формат файла;
- изображение больше 10 МБ; 
- видео больше 50 МБ;
- повреждённый файл, который невозможно декодировать;
- видео длительностью больше 30 секунд.

Для каждого негативного случая:

- HTTP-статус соответствует `api/openapi.yaml`;
- тело ошибки соответствует схеме OpenAPI;
- `movie_id` не возвращается;
- после ошибочного запроса сервис остаётся работоспособным.

Дополнительно выполнить smoke регистрации и входа:

- регистрация пользователя с корректными данными;
- вход с корректными данными;
- доступ к защищённому API после входа;
- отказ в доступе без авторизации.

Результат прогона:

- процент запросов, в которых возвращён ожидаемый `movie_id`, отдельно для image и video;
- доля image-запросов, выполненных не более чем за 10 секунд;
- доля video-запросов, выполненных не более чем за 15 секунд;
- список найденных bugs.

### Sprint 2 — поиск по тексту и аудио, восстановление пароля

Основная QA-задача — контрольная выборка поиска по тексту и аудио.

Для проверки поиска:

- использовать 10 фильмов из контрольной выборки Sprint 1;
- для каждого фильма подготовить 3 текстовых запроса и 2 аудиофрагмента;
- текстовые запросы для одного фильма должны отличаться по формулировке и описывать разные характерные элементы сюжета или сцен;
- аудиофрагменты одного фильма должны быть взяты из разных его частей;
- для каждого теста заранее зафиксировать ожидаемый `movie_id`.

Проверить:

**Поиск по тексту**

- ожидаемый `movie_id` присутствует среди результатов поиска;
- HTTP-статус и структура ответа соответствуют `api/openapi.yaml`.

**Поиск по аудио**

- система возвращает ожидаемый `movie_id`;
- HTTP-статус и структура ответа соответствуют `api/openapi.yaml`;
- не менее 95% запросов выполняются не более чем за 15 секунд.


Дополнительно проверить:

- восстановление пароля с корректными данными;
- вход с новым паролем после восстановления;
- выход из системы;
- отказ в доступе к защищённому API после выхода.

Результат прогона:

- процент аудиозапросов, в результатах которых присутствует ожидаемый `movie_id`;
- процент текстовых запросов, в результатах которых присутствует ожидаемый `movie_id`;
- доля аудиозапросов, выполненных не более чем за 15 секунд;
- список найденных bugs.


### Sprint 3 — карточка фильма, TMDB и нагрузочная проверка поиска

Проверить:

- открытие карточки существующего фильма;
- корректность основных данных фильма;
- отображение результатов поиска;
- работу пагинации;
- повторно проверить несколько ранее успешных запросов по изображению, видео, тексту и аудио;

Выполнить нагрузочную проверку поисковой цепочки.

Во время прогона проверить:

- система выдерживает целевую нагрузку согласно #17093;
- время ответа остаётся в пределах требований #17093;
- при перегрузке поисковой цепочки система возвращает HTTP 503 и после снижения нагрузки продолжает нормально работать.

Результат:

- частота запросов и длительность нагрузочного теста;
- количество выполненных запросов;
- количество успешных запросов и ошибок;
- список найденных bugs.

### Sprint 4 — личный кабинет, списки и пагинация

Основная QA-задача — проверка сквозных пользовательских сценариев.

Проверить сценарий:

1. зарегистрироваться и войти;
2. выполнить поиск фильма;
3. открыть найденный фильм;
4. добавить фильм в список «Хочу посмотреть»;
5. открыть профиль и убедиться, что фильм появился в соответствующем списке;
6. добавить фильм в список «Просмотрено» и проверить его отображение;
7. удалить фильм из одного из списков и убедиться, что изменение сохранилось;
8. проверить, что выполненные действия отображаются в истории;
9. проверить обновление статистики профиля после добавления фильма в «Просмотрено»;
10. выйти из системы и убедиться, что защищённые действия больше недоступны.

Результат:

- сквозной сценарий выполнен полностью или зафиксирован шаг, на котором возникла ошибка;
- список найденных bugs.

### Sprint 5 — Оценки, отзывы, сквозная интеграция и НФТ

Функционально проверить:

- выставление оценки фильму в диапазоне от 1 до 10;
- изменение ранее выставленной оценки;
- корректное обновление средней оценки фильма;
- создание/изменение/удаление отзыва;
- невозможность создания второго отзыва того же пользователя на тот же фильм;
- выполнение основных пользовательских сценариев предыдущих спринтов.

Проверить требования безопасности:

- защищённые API недоступны без авторизации;
- после выхода сессия больше не даёт доступ к защищённым API;
- после смены или восстановления пароля прежние сессии перестают действовать;
- после 3 неудачных попыток входа требуется CAPTCHA;
- после 5 неудачных попыток аккаунт блокируется на 15 минут;
- после окончания блокировки вход с корректным паролем снова доступен;
- при превышении 100 запросов в минуту возвращается HTTP 429;
- production доступен по HTTPS;
- PostgreSQL недоступен напрямую извне.

Выполнить нагрузочный тест системы целиком.

Во время нагрузочного теста проверить:

- система выдерживает нагрузку согласно #17093;
- время ответа соответствует требованиям #17093;
- проверяются не только поисковые запросы, но и основные пользовательские операции;
- при превышении допустимой нагрузки система возвращает предусмотренные ошибки и после снижения нагрузки продолжает нормально работать.

Результат:

- интенсивность запросов и длительность нагрузочного теста;
- количество выполненных запросов;
- количество успешных запросов и ошибок;
- результат проверок безопасности;
- список найденных bugs.

### Sprint 6 —  Выпуск: развёртывание, тестирование, демо

После финального релиза выполнить проверку системы на рабочем сервере.

Повторно проверить основные пользовательские сценарии:

- регистрация, вход, выход и восстановление пароля;
- поиск по изображению, видео, тексту и аудио;
- открытие карточки фильма;
- добавление и удаление фильмов из пользовательских списков;
- профиль, история и статистика;
- выставление и изменение оценки;
- создание, изменение и удаление отзыва;
- основные проверки безопасности.

Дополнительно повторно проверить сценарии, связанные с дефектами, исправленными после Sprint 5.

Если после финального релиза основной пользовательский сценарий не работает, нарушена целостность данных или обнаружена критическая проблема безопасности, выполняется откат релиза.

Результат:

- результат приёмочного прогона;
- список найденных bugs;
- результат повторной проверки исправленных дефектов.

## 5. Критерии завершения проверки

Проверка функциональности спринта считается завершённой, если:

- обязательные сценарии выполнены;
- ответы API соответствуют актуальному `api/openapi.yaml`;
- требования по времени ответа, относящиеся к проверяемой функциональности, выполнены;
- обнаруженные дефекты заведены в Redmine;
- отсутствуют блокирующие дефекты, препятствующие использованию основной функциональности спринта.

## 6. Работа с дефектами

Обнаруженный дефект заводится в Redmine трекером `Bug` и связывается с нарушенным требованием.

В Bug указываются:

- версия или commit, на котором обнаружен дефект;
- шаги воспроизведения;
- ожидаемый результат;
- фактический результат;
- логи или скриншоты при необходимости.

Если дефект обнаружен во время контрольной выборки поиска, дополнительно указывается соответствующий тестовый случай.

Исполнителя Bug назначает ментор соответствующего направления.

## 7. Хранение контрольных выборок

Для контрольных выборок Sprint 1 и Sprint 2 должен сохраняться воспроизводимый набор тестовых данных.

Для каждого тестового случая фиксируются:

- идентификатор теста;
- `movie_id`;
- тип запроса;
- ожидаемый `movie_id`;
- ссылка или путь к используемому файлу либо текст запроса.

После начала прогона состав контрольной выборки не изменяется без фиксации причины изменения.
