# Как мы разрабатываем DejaView

Этот документ описывает весь процесс работы: где заводить задачи, как их вести, как попадает код в проект. Если сомневаешься «а как правильно?» — смотри сюда.

## Где что находится

| Что | Где |
|---|---|
| Задачи и баги | **GitHub Issues** в соответствующем репозитории |
| Планирование и статус | **Доски Projects** (по направлениям: Backend, Frontend, ML, QA-DevOps) |
| Код | Репозитории направлений (`dejaview-backend`, `-frontend`, `-ml`, `-infra`) |
| Контракты API, архитектура, соглашения | этот репозиторий (`dejaview-docs`) |

## Жизненный цикл задачи

```
Issue заведён → Backlog → To do → In progress → In review → Done
```

1. **Backlog** — задача есть, но ещё не в работе.
2. **To do** — приоритизирована, готова к взятию.
3. **In progress** — кто-то взял и делает (назначен Assignee).
4. **In review** — открыт Pull Request, идёт ревью.
5. **Done** — PR влит в `main`, задача закрыта.

Двигать карточку по колонкам — обязанность того, кто взял задачу.

## Как завести задачу

1. Создай **Issue** в нужном репозитории (кнопка New issue → шаблон «Задача» или «Баг»).
2. Заполни: **что нужно сделать** и **критерии приёмки** (когда считаем готовым).
3. Повесь **метки**: тип (`feat`/`fix`/`bug`/…) и, если нужно, приоритет.
4. Добавь Issue на доску своего направления (колонка Backlog).
5. Когда берёшь в работу — назначь себя (Assignee) и передвинь в In progress.

## Задачи и подзадачи

Крупную задачу дроби на мелкие — так проще делать и ревьюить.

- **Чек-лист** внутри Issue — для простой разбивки:
  ```
  - [ ] Сверстать форму
  - [ ] Подключить API
  - [ ] Обработать ошибки
  ```
- **Sub-issues** (иерархия задач в GitHub) — если подзадачи крупные и их ведут разные люди: заводишь отдельные Issues и привязываешь к родительской.
- Связи между задачами описывай словами в тексте: `Часть #12`, `Блокируется #34`.

## Ветки и коммиты

Подробно — в [conventions.md](conventions.md). Кратко:

- Ветка на задачу от `main`: `feat/audio-search`, `fix/login-500`.
- Коммиты по [Conventional Commits](conventions.md): `feat: ...`, `fix: ...`, `refactor: ...`.
- Прямой push в `main` **закрыт** — только через Pull Request.

## Pull Request и ревью

1. Открой PR из своей ветки в `main`. Опиши: что сделано и как проверить (шаблон подставится).
2. В описании укажи `Closes #42` — при мерже задача закроется автоматически.
3. Нужно **одобрение ревьюера** (магистрант-куратор назначается автоматически по CODEOWNERS).
4. Ревьюер смотрит код, оставляет замечания. Правишь — снова на ревью.
5. После одобрения PR вливается в `main` (рекомендуем **Squash and merge** — один аккуратный коммит на задачу).

## Ритм работы

- **Итерации** — недельные (или двухнедельные, согласуем).
- **Планёрка** в начале итерации: что берём в To do.
- **Статус** держим актуальным на доске — не «в голове».
- **Совещания** и созвоны — по договорённости команды и куратора.

## Роли в процессе

| Роль | Кто | Что делает |
|---|---|---|
| Менеджер | Даниил | Приоритеты, координация, риски |
| Куратор направления | магистрант | Ревью PR, помощь, архитектурные решения |
| Разработчик | бакалавр | Берёт задачи, пишет код, открывает PR |
| QA | бакалавр | Тесты, заведение багов |

## Definition of Ready (задача готова к взятию)

- Понятно, что нужно сделать.
- Есть критерии приёмки.
- Нет блокеров (или они указаны).

## Definition of Done (задача завершена)

- Код работает и проверен локально.
- PR прошёл ревью, замечания закрыты.
- Документация обновлена, если менялось поведение или API.
- Задача закрыта, карточка в Done.
