# Процесс работы над DejaView

Где заводятся задачи, как они движутся и кто за что отвечает.
Техника git (ветки, коммиты, Pull Request) описана в [conventions.md](conventions.md).

## Две системы

| Что | Где |
|---|---|
| Требования, задачи, баги, учёт времени | Redmine: https://ai.nsu.ru/projects/dejaview |
| Код, ветки, Pull Request, ревью | GitHub, репозитории направлений |
| Архитектура, контракты, соглашения | этот репозиторий |

Задачи ведём только в Redmine. GitHub для кода.

## Кто заводит задачи

Задачи (трекер `Task`) создаёт и назначает менеджер проекта, в момент, когда работу
планируется начинать. Это требование методических указаний: план меняется по ходу
проекта, заводить в Redmine всё сразу смысла нет.

1. На планировании спринта ментор направления формулирует задачи своей зоны:
   состав работ, критерии приёмки, оценку в часах.
2. Формулировки уходят менеджеру, он заводит задачи и назначает исполнителей.
3. Разработчик получает задачу уже назначенной на себя.

Видите работу, которой нет в Redmine, напишите ментору направления.
Сами задачу не заводите.

Исключение: баги. Их заводит тот, кто нашёл, в трекер `Bug`.

## Статусы задачи

```
New -> In Progress -> Resolved -> Closed
```

| Статус | Значение |
|---|---|
| New | заведена и назначена |
| In Progress | исполнитель взял в работу |
| Resolved | сделано, ждёт приёмки |
| Closed | результат принят |
| Need More Info | нужны уточнения, работа приостановлена |
| Feedback | вернули на доработку с замечаниями |

## Жизненный цикл

1. Задача назначена, у неё есть сроки и оценка часов.
2. Исполнитель переводит её в In Progress и трекает время.
3. Код: ветка, коммиты, Pull Request, ревью ментора направления.
4. PR влит в `main`, задача переводится в Resolved.
5. Ментор проверяет результат по требованию, менеджер переводит в Closed.
   Нужны правки: Feedback. Есть вопросы: Need More Info.

## Учёт времени

Время логируется в задачу (`Task`), а не в требование (`Requirement`). Требование это
артефакт, а не процесс: одно требование проходит анализ, реализацию и тестирование
разными задачами, и трудозатраты на нём всё это смешают.

Без залогированного времени задача не считается сделанной.

## Definition of Ready

- Понятно, что нужно сделать, есть критерии приёмки.
- Задача связана с требованием, нет блокеров.
- Проставлены сроки и оценка часов.

## Definition of Done

- Код работает и проверен локально.
- PR прошёл ревью, замечания закрыты, влит в `main`.
- Время залогировано в Redmine.
- Документация обновлена, если менялось поведение или API.
- Задача переведена в Resolved, менеджер принял её в Closed.
